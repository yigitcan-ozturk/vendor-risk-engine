# v0.6 Evidence and Supplier Feasibility

## Objective

Add evidence-aware supplier feasibility observations without changing the existing technical-compliance boundary or inventing missing supplier facts.

## Motivation

Live RFQ workflows produce useful supplier signals before traditional KPI history is available. Examples include whether a supplier quoted, declined because of minimum quantity or capacity, could not supply the requested product range, revised an offer, or responded within a measurable period.

These observations should be represented explicitly and audibly rather than inferred from free-form correspondence.

## Proposed observation fields

| Field | Purpose |
| --- | --- |
| source_type | Origin category such as EMAIL, ERP, MANUAL_REVIEW or API |
| source_reference | Stable external or internal evidence reference |
| observation_date | Date the evidence was observed |
| quote_status | QUOTED, DECLINED, PARTIAL, NO_RESPONSE or UNKNOWN |
| feasibility_reason | MOQ, CAPACITY, PRODUCT_RANGE, AVAILABILITY, OTHER or UNKNOWN |
| revision_count | Explicit number of quotation revisions when known |
| response_days | Measured response interval when both timestamps are known |

## Rules

- Missing facts remain UNKNOWN.
- No hidden penalty is applied merely because evidence is absent.
- Raw email content is not required in structured results; store a reference/provenance pointer instead.
- Supplier feasibility is operational/commercial evidence, not technical bid compliance.
- Technical compliance remains owned by bidlint.
- Quotation price comparison remains owned by rfqdiff.
- Existing vendor and score fields remain backward compatible for supplier-scorecard.

## Implementation sequence

1. Define enums and validation.
2. Add versioned provenance/feasibility schema.
3. Add deterministic feasibility scoring policy.
4. Add CSV and history ingestion.
5. Add sample observations covering quoted, MOQ-declined, unavailable, partial and unknown cases.
6. Add tests for missing evidence, invalid enums, response timing and revision counts.
7. Expose fields through package API and CLI JSON output.
8. Integrate the resulting signal into supplier-scorecard portfolio mode.

## Acceptance criteria

- deterministic and documented behavior;
- no inference from missing correspondence;
- versioned machine-readable schema;
- backwards-compatible current scoring API;
- Python 3.11–3.13 test coverage;
- auditable source references without embedding private correspondence.
